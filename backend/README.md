# Company Chat API — Phase 1

Fastify API, PostgreSQL connection pool, Drizzle, health checks and Docker.
All application source is JavaScript ES modules. Existing later-phase files stay
empty: authentication, employees, sessions, messages and WebSockets are not implemented.

## Requirements and first start

Install Docker Desktop with Linux containers and Docker Compose v2. Local Node.js
and PostgreSQL are **not** required. Run these PowerShell commands from the
`internal-chat` root:

```powershell
Copy-Item backend/.env.example backend/.env
# Edit backend/.env: set POSTGRES_PASSWORD to a strong random password.
docker compose config --quiet
docker compose up -d --build
docker compose ps
docker compose logs --tail=100 api postgres
Invoke-RestMethod http://localhost:3001/health/live
Invoke-RestMethod http://localhost:3001/health/ready
```

If `.env` already exists, preserve it; do not overwrite working credentials.
The initial implementation creates a local ignored `.env` with a random password
for verification. Never commit or share it. Protect it with filesystem permissions.
Compose environment variables are visible to Docker administrators; use a secret
manager when deploying beyond the local foundation.

For production set `NODE_ENV=production`. If overriding `DATABASE_URL`, URL-encode
credentials. Compose credentials are encoded automatically. No secrets are baked
into images. The database has no published port. API port 3001 is bound only to
localhost. Both services share an internal Docker network.
The API and optional tools also join an ingress network for localhost port
publishing; PostgreSQL joins only the internal network.

Startup validates configuration and runs `SELECT 1` before listening. A startup
failure exits nonzero; Compose restarts the service. Pool and query timeouts bound
database failures. SIGINT/SIGTERM stop Fastify and close the pool, with a forced-exit
deadline. Request IDs are generated by the server and returned as `x-request-id`.
Raw error messages, request bodies, headers and URL queries are omitted from logs.
Development validation errors include field/rule details; production omits them.
Schema validation rejects unexpected fields where a route uses
`additionalProperties: false`.

## Docker operations

```powershell
docker compose up -d --build
docker compose ps
docker compose logs -f api postgres storage
docker compose restart api
docker compose stop
docker compose down
```

`down` preserves the named PostgreSQL volume. `down -v` **deletes database data**.
PostgreSQL initialization variables apply only when the volume is first created;
editing the password in `.env` does not change the existing database role.

The runtime image uses Node.js 24 LTS, production dependencies, a non-root user,
read-only filesystem and dropped Linux capabilities. The optional `tools` profile
uses a separate image with development dependencies. Nginx's reserved directory is
`../nginx`; no proxy or certificates are needed for Phase 1.

Container-only installation and verification:

```powershell
docker compose --profile tools build tools
docker compose run --rm tools npm run lint
docker compose run --rm tools npm test
```

Dependencies install with `npm ci` while building. `package-lock.json` is retained
for reproducible installs. If Node.js 24 is available locally:

```powershell
cd backend
npm ci
npm run lint
npm test
npm run dev
```

The scoped esbuild override patches Drizzle Kit's legacy loader dependency.
Generation and migration commands are verified with that override; retain it
until upstream removes the vulnerable transitive dependency.

For local `dev`/`start`, supply a reachable `DATABASE_URL` in `.env`; Compose's
`postgres` hostname is only resolvable inside its network. Docker is the supported
default runtime. `dev` uses Node's automatic reload.

Tests never read `.env` or use the application's `DATABASE_URL`. Failure tests
use an isolated local TCP listener that cannot speak PostgreSQL. The integration
test is skipped unless `TEST_DATABASE_URL` is explicitly supplied, and refuses
database names without the `_test` suffix. It executes only `SELECT 1`.
To run it against a separate real database:

```powershell
docker compose exec postgres sh -c 'createdb -U "$POSTGRES_USER" company_chat_test'
docker compose run --rm api node --input-type=module -e 'import { spawnSync } from "node:child_process"; import { loadEnv } from "./src/config/env.js"; const u = new URL(loadEnv().databaseUrl); u.pathname = "/company_chat_test"; const r = spawnSync(process.execPath, ["--test", "src/tests/foundation.test.js"], { stdio: "inherit", env: { ...process.env, TEST_DATABASE_URL: u.href } }); process.exit(r.status ?? 1);'
```

If that database already exists, skip `createdb`.

## Drizzle migrations

The schema entry point is `src/database/schema/index.js`; Phase 1 has no
application tables. Add future schema exports there. Migration metadata lives
under `src/database/migrations`. No automatic migrations run during API startup.

```powershell
docker compose run --rm tools npm run db:generate
docker compose run --rm tools npm run db:migrate
docker compose run --rm -p 127.0.0.1:4983:4983 tools npm run db:studio -- --host=0.0.0.0
```

Generation output persists through the tools service's database directory bind

migration journal allows migration to run with no application DDL.

keep its port restricted to localhost.

## Health and troubleshooting

`GET /health/live` returns HTTP 200:
`{"status":"ok","service":"company-chat-api"}`.
`GET /health/ready` executes a real PostgreSQL query and a storage bucket
check, then returns HTTP 200:
`{"status":"ready","database":"connected","storage":"connected"}`.
When object storage is not configured, `storage` is `unconfigured`. When the
bucket is unreachable it is `disconnected`.
On database failure readiness returns HTTP 503 with `status: "not_ready"`,
`database: "disconnected"` and a standardized error carrying the request ID.
Liveness remains 200 while the database is unavailable. The container health check
uses liveness; use readiness for traffic admission.

- Docker connection errors: start Docker Desktop and select Linux containers.
- Port 3001 busy: stop the conflicting local service before starting this stack.
- API restarting: validate `.env`, inspect `docker compose logs`, and check
  `docker compose exec postgres sh -c 'pg_isready -U "$POSTGRES_USER" -d "$POSTGRES_DB"'`.
- Readiness 503: inspect PostgreSQL health, credentials and connection timeouts.
  An existing volume may contain an older password.
- Startup errors intentionally omit raw exceptions to prevent credential leakage.
  `loadEnv` validates missing/invalid field names without including their values.
- A database outage after startup does not terminate the API; readiness recovers
  when PostgreSQL returns.

Reference documentation: [Node release support](https://github.com/nodejs/Release),
[Fastify server options](https://fastify.dev/docs/latest/Reference/Server/),
[Drizzle migrations](https://orm.drizzle.team/docs/drizzle-kit-generate).

## Phase 2: employee access and administration

Phase 2 adds employee accounts, role-based administration, Argon2id password
hashing, access JWTs, per-device refresh sessions, audit logging and OpenAPI
documentation. The browser UI is available only to an authenticated administrator
at `GET /docs`; the API specification is available at `GET /documentation/json`
under the same access control.

Run the migration once for an existing Phase 1 volume:

```powershell
docker compose --profile tools build tools
docker compose run --rm tools npm run db:migrate
```

Create the first administrator only after setting the three `BOOTSTRAP_ADMIN_*`
variables in a secure invocation environment. They are deliberately not needed by
the API container:

```powershell
$env:BOOTSTRAP_ADMIN_USERNAME = 'admin'
$env:BOOTSTRAP_ADMIN_DISPLAY_NAME = 'Initial Administrator'
$env:BOOTSTRAP_ADMIN_PASSWORD = '<a unique 12+ character password>'
docker compose run --rm `
  -e BOOTSTRAP_ADMIN_USERNAME `
  -e BOOTSTRAP_ADMIN_DISPLAY_NAME `
  -e BOOTSTRAP_ADMIN_PASSWORD `
  tools npm run bootstrap:admin
Remove-Item Env:BOOTSTRAP_ADMIN_PASSWORD
```

The command never prints a credential, creates an administrator only when none
exists, and is safe to rerun. The first login requires an immediate password
change. Do not put bootstrap credentials in source control or Compose files.

### Recover an existing administrator password

`bootstrap:admin` is idempotent: if any administrator already exists it prints
`Administrator already exists; no changes made.` and does nothing. Use the
explicit recovery command instead. It never creates a user. It requires local
operator access to the tools container (or a shell with database credentials),
an explicit `--username`, and `--confirm`.

The new password is read from stdin only. It is not accepted as a flag, npm
script argument, or environment variable, and it is not written to logs.

```powershell
docker compose --profile tools run --rm -i tools npm run recover:admin -- --username admin --confirm
```

On a TTY the command prompts twice without echo. Without a TTY, pipe the
password and confirmation as two lines:

```powershell
@"
<12-or-more-character-password>
<12-or-more-character-password>
"@ | docker compose --profile tools run --rm -T tools npm run recover:admin -- --username admin --confirm
```

Recovery Argon2id-hashes the password, sets `mustChangePassword`, revokes every
session and refresh token for that administrator, and writes `ops.admin_recovered`
to the audit log. Other employees, messages, and volumes are untouched. If the
account is suspended, login stays blocked until another administrator
reactivates it. After recovery, log in and call `POST /api/v1/auth/change-password`
before using admin APIs.

Do not recover the production administrator as a test. Create or use an isolated
username if you are only verifying the command.

### Creating employee credentials

There is no public signup. Administrators create employees with
`POST /api/v1/admin/users` after a completed password change:

```json
{
  "username": "jsmith",
  "displayName": "Jane Smith",
  "employeeCode": "E1042",
  "email": "jane.smith@example.test",
  "role": "user"
}
```

Usernames must match `^[A-Za-z0-9][A-Za-z0-9._-]*$` and are unique
case-insensitively. The API generates a one-time `temporaryPassword` (12+
characters), stores only the Argon2id hash, and requires a password change on
first login. The temporary secret is returned once in that response; deliver it
out of band and never log it. Duplicate usernames return 409. Missing
authentication returns 401. A non-admin token returns 403.

### Postman

Import `postman/company-chat.postman_collection.json` and
`postman/local.postman_environment.json` from the repository root. Set
`baseUrl` to `http://127.0.0.1:3001`. Put the administrator username and
password in the environment's **current** values (the committed file leaves
secrets empty).

Recommended native order: Admin login → Create employee → Employee login →
Change password → Employee login → Refresh token → Current profile → List
employees → Suspend / reactivate → Reset password → Revoke sessions → Logout.

Native requests must **not** send `Origin`. Web requests in the cookie folder
must send `Origin: {{webOrigin}}`, `X-Requested-With: company-chat`, and
`X-CSRF-Token` on refresh and logout; Postman stores `chat_refresh` in the
cookie jar. Do not export the collection or environment after a run if Postman
offers to include current values—that would persist passwords and refresh
tokens.

Isolated API checks against the running Compose stack use unique
`ops.recovery.*` / `ops.emp.*` usernames and never truncate the application
database.

The Compose stack includes PostgreSQL 17, the Fastify API, and LocalStack 4.4
as private S3-compatible storage on `127.0.0.1:4566`. The `storage_data` volume
persists objects. Do not publish the bucket publicly. Production `NODE_ENV`
requires `S3_ENDPOINT` and credentials.

The API prefix is `/api/v1`. `POST /auth/login` requires `username`, `password`,
`clientType` (`web` or `native`), `platform`, and `deviceName`. Native clients
receive a short-lived bearer access token and an opaque refresh token; store the
latter only in platform secure storage. A web client sends `Origin` and
`X-Requested-With: company-chat`; it receives the refresh token in a strict,
HTTP-only cookie plus a CSRF token. Browser refresh and every cookie-authenticated
state-changing request must send `X-CSRF-Token`. Configure the exact browser
origin in `CORS_ORIGINS`; production origins must use HTTPS.

Access tokens expire after 15 minutes. Refresh tokens are opaque, hashed in
PostgreSQL, rotated on every use, and expire after `REFRESH_TOKEN_DAYS` (1–90,
default 30). Replaying an already-consumed refresh token revokes that session.
Suspension, password change, password reset, logout, explicit revocation and
expiry invalidate sessions server-side. A future WebSocket gateway can subscribe
to the internal session-revocation event; Phase 2 does not add sockets.

Administrators can use `/admin/users` to create, search, update, suspend,
reactivate, reset passwords and revoke sessions, and `/admin/audit-logs` for
limited audit history. Employee endpoints are `/users`, `/users/me`, `/devices`,
and `/sessions`. User profile edits only permit display and contact fields; role,
status, username, employee code, and password hashes cannot be changed by that
endpoint.

Profile photos are JPEG, PNG, or WebP up to 5 MB. Employees start an upload with
`POST /users/me/photo`, PUT the object to the returned private URL, then
`POST /users/me/photo/complete`. `DELETE /users/me/photo` removes the current
photo. Administrators use `/admin/users/:id/photo` (init, complete, and DELETE).
The API inspects magic bytes, writes a 256×256 WebP thumbnail with `sharp`, and
stores only the object key in PostgreSQL. `GET /users/:id/photo-url` returns a
short-lived authenticated download URL. Completing or removing a photo broadcasts
`user.updated` to the employee’s other devices and conversation peers.
The temporary password returned from account creation or reset is a one-time
delivery value: present it through an approved private channel, never logs.

Each account may have at most 50 active sessions. The database locks the user
row while creating a session, so simultaneous login attempts cannot exceed the
limit. Devices are separate records from session records. Expired sessions are
marked revoked and consumed refresh-token hashes are pruned on the configured
interval.

## Phase 3 messaging

Apply the forward-only messaging migration with `docker compose run --rm tools npm run db:migrate`.
`0001_lyrical_boom_boom.sql` adds conversations, memberships, canonical direct
pairs, messages and per-user receipts without altering Phase 1/2 tables.

Key authenticated endpoints are `POST /api/v1/conversations/direct`,
`GET /api/v1/conversations`, `GET /api/v1/conversations/:id`,
`GET/POST /api/v1/conversations/:id/messages`,
`PATCH/DELETE /api/v1/messages/:id`, `POST /api/v1/messages/:id/forward`,
`POST /api/v1/conversations/:id/read`, `POST /api/v1/messages/:id/delivered`,
and the `/api/v1/groups` create/detail/update/member/role/leave/ownership routes.

Group owners manage all settings and administrators. Group administrators manage
non-owner membership and settings. Members send messages and leave. System-wide
administrators receive no implicit membership or visibility into private groups.

`GET /api/v1/ws` accepts an authenticated bearer JWT. Incoming events are
`ping`, `typing.start`, `typing.stop`, `conversation.read`, and
`message.delivered`. Events use `{ event, eventId, timestamp, data }`. Delivery
is recorded only after a client acknowledgement, once per user account across
devices. Read positions are monotonic and exclude the sender’s own messages.
Use REST history with `afterSeq` for new messages after reconnect. Use
`GET /api/v1/conversations/:id/sync?afterChangeSeq=` to recover edits and
deletes of older messages whose original sequence is behind the client's saved
cursor. WebSocket notifications are at-least-once, not persistent delivery.

### Phase 3 group, receipt and socket behavior

`POST /api/v1/groups` creates a group with the caller as owner. Owners manage
roles and ownership; owners and group administrators can change group details
and add or remove non-owner members. A group owner must transfer ownership
before leaving or being removed. `GET /api/v1/groups/:id/members` returns active
members. `GROUP_MEMBER_LIMIT` is a validated integer from 2 through 10,000
(default 1,000); the group row is locked before a member is counted or added, so
concurrent additions cannot exceed the limit.

Creating a group and changing membership, roles or ownership produces an ordered
persisted system message. Normal messages use a per-conversation sequence and a
client message UUID for idempotency. Repeating the same `clientMessageId` in the
same conversation returns the original message with HTTP 200 and does not
increment the sequence or emit another `message.created` event. Concurrent
retries are serialized on the conversation row. REST history is cursor-based
with `afterSeq` and `limit` (1–100, default 50), ordered by sequence, and
includes soft-deleted tombstones in that sequence range. `0002_glamorous_morlocks.sql`
adds `conversations.last_change_seq` and `messages.change_seq`. Create, edit,
delete and group system messages increment the change cursor. Reconnecting
clients call `GET /api/v1/conversations/:id/sync?afterChangeSeq=` and upsert by
message `id` so older edits/deletes are recovered without duplicating rows.

Only the author may edit or soft-delete a text message, and only within 15
minutes of `createdAt`. Edits emit `message.updated`; deletes clear `content`,
set `deletedAt`, and emit `message.deleted`. System messages cannot be edited,
deleted, or forwarded. Replies must reference a non-deleted message in the same
conversation. Forwarding copies caller-supplied content into an authorized
destination conversation and stores `forwardedFromMessageId`; the caller must
be an active member of both conversations. Non-members do not receive these
WebSocket events.

Delivery is recorded only when a client sends `message.delivered`; it is one
idempotent receipt per user across that user's devices. `conversation.read`
advances a monotonic cursor and records reads for messages from other senders.
Unread totals exclude the caller's own messages and include unread system
messages.

Connect to `GET /api/v1/ws` with a valid bearer access JWT. The server emits
`connection.ready`, message/conversation/group update events, `receipt.updated`,
`typing.updated`, `presence.updated`, `session.revoked`, and `error`; each event
uses `{ event, eventId, timestamp, data }`. Clients may send `ping`,
`typing.start`, `typing.stop`, `message.delivered`, and `conversation.read`.
Payloads are bounded, validated, rate limited, and checked against current
membership. The gateway pings every `WS_HEARTBEAT_INTERVAL_MS` (10–60 seconds,
default 30 seconds). Presence is sent only to active participants who share a
conversation with the user, once for the first connection and once after the
last connection closes.

A removed member receives a one-time `group.member_removed` notification targeted
at that user, then is excluded from later private group events (updates,
membership changes, messages, typing, and receipts). Unrelated users never
receive those events. Membership is re-checked for message writes, edits,
deletes, typing, delivery acknowledgements, read updates, and history reads;
rejected operations do not change database state.

Revoking a session removes its sockets from the connection registry immediately,
emits `session.revoked`, and closes them with code 4001. Other sessions for the
same user stay connected and continue to receive group events. Presence goes
offline only when the last remaining session disconnects.

`GET /api/v1/conversations/:id` includes each member's `lastReadSeq`.
`GET /api/v1/conversations/:id/receipts` returns current delivery/read rows for
the conversation. `GET /api/v1/conversations/:id/sync` returns `{ data, nextAfterChangeSeq, lastChangeSeq, lastMessageSeq }`.

## Frontend integration (React + Vite + JavaScript)

The backend is ready for a JavaScript Vite SPA. Do not point the browser at
Compose's internal `postgres` hostname. Set:

```
VITE_API_BASE_URL=http://127.0.0.1:3001
```

WebSocket URL is `VITE_API_BASE_URL` with `http` replaced by `ws`, path
`/api/v1/ws`. For local Vite bind the app to `http://127.0.0.1:5173` (not
`localhost`) so `SameSite=Strict` refresh cookies stay first-party, and set
`CORS_ORIGINS=http://127.0.0.1:5173`. Browser cookie auth requires CORS
`credentials: true` against that exact origin. Production CORS origins must
be HTTPS.

### Authentication and token refresh

Browser login uses `clientType: "web"` and `platform: "web"`, plus
`X-Requested-With: company-chat` and a matching `Origin`. The API sets httpOnly
`chat_refresh` on `/api/v1/auth` and a readable `chat_csrf` cookie. Refresh
sends `X-CSRF-Token` and does not put the refresh token in the JSON body.
Native clients send `clientType: "native"` without browser Origin/cookies and
receive `refreshToken` in the body. Access JWTs last 900 seconds (`Authorization:
Bearer`). `POST /api/v1/auth/refresh` rotates the refresh token; reuse is
detected and revokes the session. `GET /api/v1/auth/me` returns the current
user. Logout revokes the current session (or all sessions). Must-change-password
accounts are limited to `/auth/me`, `/auth/change-password` and logout.

### User and group APIs

Authenticated employees use `/api/v1/users/me` and session/device routes.
Administrators use `/api/v1/admin/users` for create, list, suspend, reset and
session revoke. Groups: `POST/GET/PATCH /api/v1/groups`, member add/remove/role,
`transfer-owner`, and `leave`. Owners manage roles and ownership; owners and
group admins manage non-owner members and settings.

### Message APIs

Direct chats: `POST /api/v1/conversations/direct`. History:
`GET /api/v1/conversations/:id/messages?afterSeq&limit`. Send:
`POST /api/v1/conversations/:id/messages` with required `clientMessageId` and
`content`; optional `replyToMessageId`. Edit/delete: `PATCH/DELETE /api/v1/messages/:id`
(author, 15-minute window; edit is text-only). Forward: `POST /api/v1/messages/:id/forward`
(attachment forwards copy the object server-side). Read:
`POST /api/v1/conversations/:id/read`. Delivered:
`POST /api/v1/messages/:id/delivered`. Persist both `lastMessageSeq` and
`lastChangeSeq` per conversation.

### Attachment APIs

Small files still use a single presigned PUT. Files over 8 MiB, or any upload
with `strategy: "multipart"`, use resumable S3 multipart. Finalize never loads
the object into memory: it streams a prefix/tail for magic-byte inspection,
rejects executables, SHA-256s the object as a stream, then creates a sequenced
message. Unverified objects are never downloadable.

- `POST /api/v1/conversations/:id/attachments`
  `{fileName,mimeType,sizeBytes,strategy?}` → `{id,mode,uploadUrl?,partSize,partCount,headers,expiresAt,maxBytes}`
- `POST /api/v1/attachments/:id/parts` `{partNumbers}` → short-lived part PUT URLs
- `GET /api/v1/attachments/:id/parts` → already-uploaded parts for resume
- Browser `PUT` to `uploadUrl` or each part URL (do not buffer the whole file)
- `POST /api/v1/attachments/:id/finalize` `{clientMessageId,caption?,replyToMessageId?,parts?}`
  → message with `messageType` `image`/`video`/`audio`/`file` and public
  attachment metadata (no `storageKey`)
- `GET /api/v1/attachments/:id/url` → short-lived signed GET (members only;
  `available` attachments whose parent message is not deleted)
- `DELETE /api/v1/attachments/:id` cancels a pending upload (and aborts multipart)
  or deletes an available file and its message

Allowed types: JPEG/PNG/WebP/GIF (25 MiB), MP4/WebM/QuickTime video (2 GiB),
MPEG/MP4/OGG/WAV/WebM audio (100 MiB), PDF/ZIP/DOCX/XLSX/PPTX (2 GiB),
text/plain (8 MiB). Images, video, and audio are served with
`Content-Disposition: inline`; documents use `attachment`.
Daily quota and unfinished-upload limits apply. Abandoned pending/quarantined
rows are deleted by the cleanup job after `ATTACHMENT_PENDING_TTL_MS`.

### WebSocket event payloads

Connect to `GET /api/v1/ws` with the access JWT. Node clients may send
`Authorization: Bearer`. Browsers cannot set that header; they must open
`new WebSocket(url, ['company-chat', accessToken])` so the JWT is carried in
`Sec-WebSocket-Protocol`. Every frame is
`{ event, eventId, timestamp, data }`. Server events include `connection.ready`
(`userId`, `sessionId`), `conversation.created` / `conversation.updated`,
`message.created` / `message.updated` / `message.deleted`, `group.member_added`,
`group.member_removed`, `group.member_updated`, `group.member_left`,
`group.owner_transferred`, `receipt.updated`, `typing.updated`,
`presence.updated`, `session.revoked`, `pong`, and `error` (`code`). Clients send
`ping`, `typing.start`, `typing.stop`, `message.delivered`, and
`conversation.read`. Close code 4001 means unauthorized or revoked.

### Reconnection and synchronization

1. Refresh the access token if needed. Expired or revoked JWTs cannot open a
   socket (close 4001).
2. Reopen `/api/v1/ws`.
3. `GET /api/v1/conversations/:id/sync?afterChangeSeq=` and upsert messages by
   `id` (apply `editedAt` / `deletedAt` even when `sequenceNumber` is not new).
4. `GET /api/v1/conversations/:id/messages?afterSeq=` if only new rows are
   needed.
5. `GET /api/v1/conversations/:id` for membership and `lastReadSeq`;
   `GET /api/v1/conversations/:id/receipts` for delivery/read rows.
6. Replay unsent messages with the same `clientMessageId` (HTTP 200 means
   duplicate, do not append again).
If the user was removed from a group while offline, group and conversation
routes return 403/404.

### Error responses

Failed requests return `{ error: { code, message, requestId } }`. Validation
may include `details` outside production. Rate limits return 429. Do not log
tokens, passwords or message bodies in the frontend.

The React + Vite client in `../frontend` consumes these APIs. Bind Vite to
`http://127.0.0.1:5173` so strict cookies and LocalStack CORS stay first-party.

## Phase 5: secure media and file sharing

Migration `0003_neat_ricochet.sql` extends `message_type` with `image`, `video`,
`audio`, and `file`, and creates `attachments` (`pending`, `quarantined`,
`available`, `rejected`, `deleted`). Apply it once against the existing volume:

```powershell
docker compose --profile tools run --rm tools npm run db:migrate
```

Do not run `docker compose down -v`. Isolated tests use `company_chat_test` and
`S3_TEST_BUCKET=company-chat-test`. Inside the tools container, construct
`TEST_DATABASE_URL` from `POSTGRES_*` (Compose does not inject `DATABASE_URL`
into tools) and set `S3_PUBLIC_ENDPOINT=http://storage:4566` so presigned PUTs
stay on the Docker network.

Object storage is LocalStack S3, not a public bucket. Credentials never appear
in API responses. Content inspection uses `file-type` magic bytes plus PE/ELF/
Mach-O/shebang rejection. There is no ClamAV daemon in this stack; files sit in
`quarantined` until inspection succeeds.
